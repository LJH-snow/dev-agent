## 根修复方案：在 Ink 输入协议边界拦截 Kitty 查询响应

### 根因
Ink 7.1.1 启动时在 stdin 上临时监听 `data` 事件发送 `ESC[?u` 查询；App 的 `useInput` 同时通过 `readable` 读取 stdin。某些终端返回 `ESC[?0u` 时，探测器虽然看到了响应，但同一字节仍会被 App 的输入解析器读取。Ink 的 CSI parser 接受 `?0u`，而 Kitty 按键解析只接受数字开头的 CSI-u，于是 `useInput` 最终收到 `[?0u` 并把它当作普通 composer 文本。

不把 `[?0u` 当作普通文本做事后删除，也不关闭 Kitty keyboard protocol；修复点放在 CLI 唯一的 `useInput` 协议路由入口，保留 Shift+Enter 和不支持 Kitty 的终端回退行为。

### 实施步骤

1. **新增有状态的 Kitty query response 过滤器**
   - 新建 `apps/cli/src/ink/kitty-query-response.ts`。
   - 只识别 Kitty 探测响应 `ESC[?数字u` 及 Ink 去掉 ESC 后的 `[?数字u` 形式。
   - 维护一个很小且有界的 pending 前缀，处理 `ESC`、`[?`、数字和 `u` 被 Ink/PTY 拆成多个 input event 的情况。
   - 完整响应被消费，不产生 composer 输入；响应前后相邻的真实字符原样返回。
   - 遇到不符合协议的内容时立即释放 pending 文本，避免吞掉普通 CSI、方向键、Shift+Enter、paste 内容或用户实际输入；pending 长度设上限，避免异常终端数据造成无界缓存。
   - 导出纯函数/小类 API，便于单测，不依赖 Ink 私有模块，也不修改 `node_modules`。

2. **接入 `InkCliApp` 输入路由**
   - 在 `apps/cli/src/ink/app.tsx` 的 `useInput` 回调最前端（editor `inputSuppressed` 之后、鼠标和按键分支之前）使用 `useRef` 持有过滤器。
   - 过滤器返回空结果时直接结束本次事件；返回结果时再进入现有鼠标、Kitty press/release、快捷键、提交和文本插入逻辑。
   - 保持现有 `kittyKeyboard: {mode: "auto", flags: ["disambiguateEscapeCodes"]}`，这样支持 Kitty 的终端仍保留 Shift+Enter，非 Kitty 终端仍然安全回退；不通过强制 `enabled` 换取表面上没有查询响应的副作用。

3. **补充协议级单元测试**

   - 测试断言只吞掉精确的 Kitty query response，不吞普通 Kitty CSI-u（如 Shift+Enter）、方向键或普通文本。

4. **补充真实 Ink composer 回归测试**

     - 将响应拆成多个 stdin chunk，并覆盖超过 Ink pending-escape flush 延迟后再发送 `u` 的情况；
     - 响应前后夹带真实字符，显式 Enter 后只提交真实字符；
     - 现有 Shift+Enter、Kitty release、bracketed paste 用例继续通过。
   - 如需触发 Ink auto probe，给 harness 增加可选 render options，仅在回归用例开启 `kittyKeyboard: {mode: "auto"}`；普通测试保持无探测，避免改变现有 fixture 时序。
