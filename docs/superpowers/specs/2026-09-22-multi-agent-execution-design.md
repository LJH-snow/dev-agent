# Multi-Agent Collaborative Execution Design

Date: 2026-09-22

## Goal

Turn the existing `:team` specialist-planning flow into a safe, observable
execution flow. A request is decomposed into a validated task DAG, runnable
tasks execute in bounded parallelism inside isolated Git worktrees, every task
can fail/retry/cancel independently, and the lead agent presents a bounded
diff/test review before any change is merged into the current working tree.

## Compatibility

- Keep `runCollaborativePlan` unchanged for callers that only need a read-only
  specialist plan.
- Add a separate `runCollaborativeExecution` API in Agent Core.
- Keep normal prompts, `:plan`, and `:apply` behavior unchanged.
- `:team <request>` uses collaborative execution in the Ink UI and leaves the
  result in a review state.
- `:team plan <request>` remains an explicit read-only planning command.
- `:team apply` is the only command that can merge a completed team result.

## Architecture

### Agent Core

`collaboration-execution.ts` owns the provider-neutral execution lifecycle:

1. Normalize and validate task IDs and dependencies.
2. Reject missing dependencies and cycles before starting any work.
3. Start every ready task whose dependencies completed, up to
   `maxParallel`.
4. Create an isolated workspace through an injected workspace provider.
5. Run an `AgentLoop` in that workspace with a unique session and an
   execution-safe approval policy.
6. Inspect the workspace and retain a bounded diff/result summary.
7. Retry only the failed task up to its configured retry limit.
8. Cancel a task without cancelling unrelated ready/running tasks.
9. Mark dependent tasks blocked when a prerequisite cannot complete.
10. Return a review object; do not merge anything.

The workspace provider is injected so Agent Core does not depend on Git or the
local filesystem layout. A provider exposes create, inspect, dispose, and
merge operations. The CLI supplies a Git worktree provider.

### CLI workspace provider

The CLI provider creates detached worktrees below a temporary collaboration
directory. It starts from `HEAD`, overlays the caller's tracked diff and
workspace-relative untracked files into each worktree, and never writes to the
current worktree during execution. It captures `git diff --binary` and status
metadata for review, removes worktrees during cleanup, and merges only after
`:team apply` confirmation.

Merging is fail-closed: the provider runs `git apply --check` against the
current working tree first. A conflict returns a review error and leaves both
the current worktree and the team result untouched.

### Ink UI

`InkRuntimeStore` gains a collaboration snapshot containing:

- task id, title, role, dependency count, attempt, status, duration;
- isolated workspace status;
- bounded error/diff/test summary;
- overall review state.

`CollaborationPanel` renders a compact live task board. It does not render
model reasoning or secrets. On completion it shows the merge instruction and
available retry targets.

## Status model

Task statuses are:

- `queued`
- `blocked`
- `running`
- `retrying`
- `completed`
- `failed`
- `cancelled`

The overall collaboration status is:

- `running`
- `review`
- `merged`
- `failed`
- `cancelled`

## Failure and cancellation

- A task failure is recorded and retried only for that task.
- A task with an incomplete failed dependency becomes `blocked`.
- Cancelling one task aborts its model/tools and prevents its workspace from
  being merged; unrelated tasks continue.
- Cancelling the overall run aborts all active tasks and leaves no mergeable
  result.
- Cleanup is attempted for every workspace, including failed tasks.

## Security boundaries

- Worktree paths are generated by the provider and are not model-controlled.
- Agent write tools are scoped to the task worktree through
  `AgentContext.workingDirectory`.
- Dangerous shell/git patterns remain denied for workers.
- Review output is size-bounded and terminal-sanitized by the CLI.
- `:team apply` is the only merge entry point.
- A failed `git apply --check` never falls back to forceful or destructive
  commands.

## Verification

- Agent Core tests cover DAG validation, dependency ordering, bounded
  parallelism, retries, per-task cancellation, blocked dependents, and
  cleanup.
- CLI tests cover worktree command sequencing, diff review, conflict
  rejection, Ink store/panel projection, and `:team apply`.
- Existing Agent Core, CLI, executor, tools, and package smoke suites remain
  green.
