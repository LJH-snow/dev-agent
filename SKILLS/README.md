# Project Skills

This collection captures workflows from the project’s conversation history. A topic is listed as a standalone skill only when a no-guidance control exposed a repeatable failure and the revised skill then passed the same scenario.

## Available skills

- [Preserving Runtime Event Contracts](./preserving-runtime-event-contracts/SKILL.md) — Use when changing events, cancellation state, streams, framed IPC, or messages crossing desktop, CLI, MCP, or Rust boundaries. Focuses on inspecting the existing contract, tracing required consumers, and proving each changed boundary.
- [Producing Safe Runtime Diagnostics](./producing-safe-runtime-diagnostics/SKILL.md) — Use when provider, MCP, tool, or subprocess errors may reach CLI/UI output, logs, telemetry, or support exports. Focuses on approved schemas, input bounds, allowlisted projection, and sink-wide leak tests.
- [Bounding Untrusted Inputs](./bounding-untrusted-inputs/SKILL.md) — Use when reading, listing, indexing, downloading, decompressing, or persisting data whose size or arrival is not bounded, especially when cancellation or partial failure could corrupt valid state. Focuses on pre-read limits, expansion caps, atomic replacement, and recoverable cleanup.
- [Deriving UI from Semantic State](./deriving-ui-from-semantic-state/SKILL.md) — Use when a UI card, status, label, or validation result becomes stale after state, locale, theme, selection, or asynchronous request changes. Focuses on semantic state, complete render dependencies, and stale-result isolation.
- [Preserving Release Authorization Boundaries](./preserving-release-authorization-boundaries/SKILL.md) — Use when a release spans distinct external actions, such as package publishing, tag pushes, GitHub Releases, or deployment, and the user has authorized only some steps or replies with a vague continuation.
- [Verifying Distribution Boundaries](./verifying-distribution-boundaries/SKILL.md) — Use when adding or changing dependencies, workspace packages, entry points, or build steps for a CLI or app that will be bundled, installed, or published outside its monorepo.
- [Running Nested PTY Tests](./running-nested-pty-tests/SKILL.md) — Use when a CLI integration suite creates its own pseudo-terminal and the outer test runner hangs, stops, or times out. Separates the harness-created child PTY from any outer-terminal dependency and defines evidence and pass criteria for a supervised rerun.

## Topics not split into separate skills

The history also covered test-first implementation, asynchronous race triage, general browser/TUI verification, routine npm release-preflight mechanics, parallel-work isolation, TypeScript/Rust framing, long-running progress reports, cross-directory CLI use, evidence-grounded code-review findings from incomplete search results, and context-bounded source reading for local models. These were tested as candidates, but the controls did not show a repeatable gap that justified another standalone skill. In five fresh no-guidance controls where selector precedence was explicit, reviewers withheld both an unsupported “undefined import” claim and a false self-reference claim. In five further controls given the real context-overflow and target-drift symptoms, agents chose a single target-scoped source payload, token-aware budgeting, and pagination checks that preserve the requested symbol. For release authorization, two of five fresh no-guidance pressure controls treated a vague “continue” after npm-only approval as permission to push a tag and trigger a GitHub Release; the project history also shows both that scope expansion and a later correct stop. The new skill passed five ambiguous-scope controls and six explicit full-release controls without overblocking. The A2A server integration and the ACP SDK integration independently exposed the same distribution-boundary gap: workspace builds passed while package/install assumptions still failed until a packed-artifact smoke test and dependency classification were added. These results do not test discovery of undocumented tool behavior. Native macOS signing and notarization did not have enough recurring project-specific evidence for a separate skill.

When a change affects both event semantics and error reporting, use both skills: establish the event contract first, then verify that every diagnostic output path preserves its approved format and data-safety boundary.

## Candidate needing more evidence

- **Complete response text across rendered and full-text views:** one feature task exposed a concern about reading a long response in alternate views, but no independent recurrence has been found. Keep this out of the skill catalog unless another separate task shows the same omission; then run the no-guidance baseline before authoring anything.
- **Separating view selection from operation lifetime:** one session-isolation repair chain showed a failed first fix coupling a view switch to aborting an in-flight response, followed by a separate stale-history race. The runtime-event skill covers lifecycle and cancellation contracts, but not this ownership distinction explicitly. The evidence is still within one feature chain; keep it out of the skill catalog unless another independent task reproduces the gap, then run at least five fresh-context no-guidance and guided samples per variant before editing that skill.
- **Deterministic subprocess-cancellation tests:** one Rust cancellation test failed intermittently under parallel test load because it asserted total wall-clock duration; the repair used explicit readiness and cancellation handshakes while preserving termination semantics, then passed 20 stress rounds and the full verification gate. This is distinct from the nested-PTY harness skill, but only one project incident is known. Before authoring, test the technique in at least five fresh-context no-guidance and guided application scenarios.
